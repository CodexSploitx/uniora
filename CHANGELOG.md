# Changelog

All notable changes to UNIORA. Packages are released in lockstep, so one version number covers all of them. The format follows [Keep a Changelog](https://keepachangelog.com/).

## 0.8.0 - 2026-10-10

No migration. The access rules are opt-in: code that does not wrap its storage with `createGuardedStorage` or pass `access` to the invitation service behaves as before, apart from the small additions under "Changed".

### Added

- **Access administration: anti-escalation when giving roles in an organization.** `createAccessAdminService` is the organization-level sibling of `TeamService` and the only door for changing who has what: `assignRole`, `unassignRole`, `blockMember`, `suspendMember`, `unblockMember`, `removeMember`, `createRole`, `updateRole`, `setRolePermissions`, `grantRolePermission`, `revokeRolePermission`, `cloneRole` and `deleteRole`. It checks the actor with the engine inside the same transaction (and under a per-organization lock) and enforces four rules: (1) you can give a role, or invite with it, only if you hold every permission it carries; (2) nobody changes their own roles, status or membership (also through another linked identity); (3) you cannot touch someone who holds permissions you do not (an Owner, for example); (4) the Owner role moves only through `assignOwnerRole` / `unassignOwnerRole`. Powers are compared as implication-closed permission sets. Refusals throw `AccessError` (`access_forbidden`, `access_self_change`, `access_escalation`, `access_target_stronger`, `access_owner_protected`) and the rule refusals are audited as `access.change_refused`. Needs `members.roles.manage`, `members.invite`, `members.block`, `members.remove` and `roles.manage` (`ACCESS_PERMISSIONS`).
- **`createGuardedStorage(storage)`** wraps any backend (memory, SQLite, Postgres, your own) so that the writes covered by the rules (memberships with roles, roles and their permissions, invitations) are refused without a single-use `AccessAuthorization` (one operation, one target, 60 s) that only the access service, the invitation service and `createTrustedAccessStorage` (for your own back office, seeds and jobs) can issue (`access_authorization_required`). `createAccessAdminService` refuses an unguarded storage unless `allowUnguardedStorage` is set. The repositories accept an optional trailing `authorization` that a plain storage ignores.
- **Invitations**: `createInvitationService({ access })` applies rule 1 when inviting, re-resolves the inviter's power when the invitation is accepted (the roles the inviter can no longer give are skipped and listed in the new `rolesSkipped` of the result), serializes with the same lock and refuses self-invitations through a linked identity.
- **HTTP**: `runAccessCommand` / `accessErrorToHttp` in core, `accessCommand` (Express) and `accessCommandRoute` (Next), with strict field shapes. The invitation `acceptUrl` is hidden from the response unless `includeAcceptUrl` is set.
- **Conformance**: `defineAccessScenarios` (also called by `defineStorageConformance`) runs the rules, the token binding, concurrency and the invitation flows on memory, SQLite and PostgreSQL.
- **Studio**: the activity feed labels `access.change_refused` in English and Spanish.
- Guide: `guides/access-admin.md`.

### Changed

- `AcceptInvitationResult` has a new `rolesSkipped` field (empty unless the inviter lost power before acceptance); the Express and Next accept routes return it.
- New audit action `access.change_refused`.

### Fixed

- **PostgreSQL: a suspension that ends within milliseconds no longer fails.** `memberships.suspend` with an end date 1 to 3 ms ahead failed about 6% of the time with check violation `23514` (`memberships_blocked_until_consistent`): `blocked_at` came from the database clock and `blocked_until` from the caller's, so the row could be written after the end date had already passed. `blocked_at` is now clamped to just before `blocked_until` and the member simply reads as active again. SQLite and memory were not affected.

## 0.7.0 - 2026-10-09

Includes new migrations: Postgres `0040`–`0041`, SQLite `0025`–`0026` (run `uniora migrate`; the new tables are small and the migrations are quick). **Breaking for custom storage implementations only (0.x):** `UnioraStorage` and `UnioraTransaction` now require a `policies` repository; the memory, SQLite and PostgreSQL storages, `createAuditedStorage` and the conformance suite already provide it. Code that only calls the repositories is unaffected.

### Added

- **Policies**: declarative rules that only ever RESTRICT what roles allow, per organization. A policy is data, never code: a JSON condition over a closed set of operators (`all`, `any`, `not`, `exists`, `eq`, `neq`, `lt`, `lte`, `gt`, `gte`, `in`, `contains`, `intersects`, `feature`, `permission`) evaluated with three values (allow, deny, indeterminate; indeterminate never allows, an explicit deny always wins, order does not matter) under hard limits on size, depth and work. Kinds `access`, `resource`, `scope` and `feature`; effects `deny` and `require` (there is no `allow`). Conditions read `subject.*` (membership, roles, active teams, always from storage), `resource.*` (stated by your server code) and declared resource attributes. `engine.authorize()` returns the verdict, a stable reason code, the policy-set revision and every policy used with its revision and hash; it never throws and fails closed. Policy administration (`policies.read`, `policies.manage`, `policies.activate`, never subject to policies, optional separation of duties) goes through `createPolicyService`, which is the only way to change policies for a user: the storage refuses every write without a short-lived `PolicyAuthorization` (`policy_authorization_required`), and all three backends enforce lifecycle (draft, active, disabled, retired), immutable revisions, limits and per-organization isolation with composite keys and triggers. `simulate` answers "what would be decided?" with an optional candidate definition. Audit: every change with the actor in the same transaction (`policy.*`), plus `createPolicyDecisionAuditor` for decisions. Also: `runPolicyCommand` / `policyErrorToHttp`, Express `policyCommand` and `authorizeResource`, Next `policyCommandRoute`, `authorizeResourceRoute` and `assertAuthorized`, a read-only **Policies** tab in Studio (English and Spanish), `definePolicyConformance` in the conformance suite and `guides/policies.md`. Later phases (team-hierarchy scope inheritance, contextual and temporal conditions, sensitive-action policies) are designed in the guide and not implemented.

### Security

- **Policies red-team fixes** (Postgres `0041`, SQLite `0026`; none of this was published before). (1) `updatePolicy` and `activatePolicy` decided what permission was needed from the state they read, then wrote without pinning that version: a change landing in between let someone with only `policies.manage` edit the definition of a policy that had just been activated, and could activate a revision written after the separation-of-duties check. The write is now pinned to the version that was checked and a change in between is `policy_version_conflict`. (2) The policy-set revision restarted at 1 for an organization deleted and created again under the same id, so another process could keep using the old organization's cached policies: revisions now come from one counter shared by all organizations and are never reused (they are no longer consecutive; compare them with `===`). (3) Names every object inherits (`constructor`, `toString`) were accepted as declared resource attributes and made the policy indeterminate forever: attribute lookups are now own-property only. (4) The `createPolicy` command accepted a client-chosen id, and ids are unique across organizations, so a caller could probe whether an id existed in another organization: the id is now always generated by the server.

## 0.6.1 - 2026-10-09

Includes new migrations: Postgres `0039`, SQLite `0024` (run `uniora migrate`; on a table with millions of rows read `guides/performance.md` first: the SQLite migration builds the search tables in about a minute per five million memberships, and the Postgres one builds its indexes while blocking writes). No breaking change for code that only calls the repositories.

### Added

- **`count({ limit })` and `countByOrganization(ids, { limit })`**: memberships, organizations, invitations and roles can stop counting at `limit`, so a total next to a list costs one page of work even when millions of rows match. Memory, SQLite and Postgres; the conformance suite covers them.
- **Studio: everything it was missing.** Members show their state (active, suspended, blocked) and when they were last active, can be filtered by state, and an operator can block, suspend until a date or restore access with a reason; organizations show and can change their state (active, suspended, archived) with a reason; the Teams tab opens at the top of the tree and shows the sub-teams of the selected team; invitations show the teams they offer; the Activity feed has a label in English and Spanish for every audit action Core records (a test enforces it); the features catalog marks features that are on by default; a read-only **Platform** page lists platform administrators and roles; numbers use the language's separators; tables and headers no longer overflow on a phone.

### Changed

- **Studio never loads or counts a whole table on the request path.** Every list is keyset-paged; totals next to a list are capped ("10,000+", "1,000+" when filtered) and the exact whole-table totals are cached and refreshed in the background (the first request answers with the capped count). Studio pages answer in 20–60 ms on 5,000,000 memberships (SQLite and PostgreSQL), see `guides/performance.md`.

### Performance

- **Text search is indexed on both engines.** SQLite: FTS5 trigram tables kept by triggers (migration `0024`); PostgreSQL: `pg_trgm` GIN indexes (migration `0039`), with the candidate ids looked up first so the planner cannot choose a bad plan, and a short walk of the first rows for terms that are common. Results are unchanged: each candidate is still checked with the exact predicate. Terms of fewer than three characters still scan.
- **New indexes** on memberships by `(provider, subject)` (everything that starts from an identity) and by `(status, id)` (the cross-organization "blocked members" view). Filters on the effective status (`suspended`, `blocked`) use the stored status as a prefilter so the index answers them.
- **SQLite optional filters use their indexes.** The executor resolves `(?N is null or column = ?N)` groups before preparing the statement; before, those queries could not use an index at all.
- **Per-organization counts are bounded**: `countByOrganization` computes each organization's count with a limit instead of a grouped scan of every row.

### Fixed

- **Deleting the last Owner always reports `last_owner`.** `memberships.delete` and `unassignOwnerRole` on the organization's last Owner (active, or the only one left) now throw `MembershipError` with the explicit code `last_owner` in the memory, PostgreSQL and SQLite backends, instead of relying on the code being inferred from the message; only an id that does not exist is `membership_not_found`. On PostgreSQL the verdict of `delete` (deleted / refused as the last Owner / never existed) is now read in the same statement, so it can never come from a different snapshot than the refusal. The conformance suite pins it for every backend: through the plain storage, inside `storage.transaction`, through `createAuditedStorage`, after a block attempt, and with two Owners deleted at once.

## 0.6.0 - 2026-10-08

Includes new migrations: Postgres `0037`–`0038`, SQLite `0022`–`0023` (run `uniora migrate`). Nothing here breaks existing code: the platform scope is a separate `PlatformStorage`.

### Added

- **Platform administrators** (a scope apart from organizations): who administers the whole project. `PlatformStorage` (`platformRoles`, `platformMembers`, plus the audit log) is a SEPARATE object from `UnioraStorage`, so it is not a breaking change and organization code never holds it. Platform roles are sets of `platform.*` permissions (prefix wildcards such as `platform.organizations.*`; `platform.*` only on the system role **Platform Administrator**, `platform_admin`); members are exact identities (links are never followed). `createPlatformEngine` (`can`, `permissionsOf`, fail-closed, optional `onDecision`), `createPlatformService` (the only way to change roles and members: no self-promotion, no escalation above your own permissions, the last active administrator is protected, optional `stepUp`, audited with the actor as global `platform.*` entries in the same transaction; plus `listOrganizations`, `setOrganizationStatus`, `grantSupportAccess` for yourself and `revokeSupportAccess`), `bootstrapPlatform` (works once) and `runPlatformCommand` / `platformErrorToHttp` with `platformCommand` (Express) and `platformCommandRoute` (Next) and the guards `requirePlatformPermission` / `assertPlatformCan`. **The storage enforces it**: every write needs a `PlatformAuthorization` (usable once per operation) that only the service and the bootstrap can issue (`platform_authorization_required`), and the databases refuse leaving the platform without an active administrator (`platform_last_admin`) or changing a system role, with triggers, against any SQL client. Backends: `createMemoryPlatformStorage`, `createPostgresPlatformStorage` (own schema `uniora_platform`, migration `0037`) and `createSqlitePlatformStorage` (migration `0022`); `definePlatformConformance` in the conformance suite. CLI: `uniora platform init --admin provider:subject` and `uniora platform status`. New audit actions `platform.*`. See `guides/platform.md`. Postgres tests now run their files one after another (they share one test database).

### Security

- **Platform scope red-team fixes** (Postgres `0038`, SQLite `0023`; none of this was published yet). (1) A plain `UPDATE` of `member_roles` (moving the last administrator's link to another role or member) skipped the last-admin guard in both databases: both now guard it. (2) SQLite `INSERT OR REPLACE` removed the last administrator, or overwrote the system role, without firing any trigger: `BEFORE INSERT` triggers now abort the conflict (`platform_duplicate`); ids can no longer change; `is_system` cannot be switched on and only `platform_admin` can be a system role or carry `platform.*` (also a CHECK in Postgres). (3) Postgres: two administrators suspending each other under `REPEATABLE READ` both succeeded and left none: the guard now refuses that isolation level, and the platform storage opens `READ COMMITTED` transactions. (4) A `PlatformAuthorization` can be used once per operation (it was replayable for 60 s). (5) `stepUp` ran before the permission check, so anyone could trigger the host's re-authentication flow: it now runs only for actors who hold the permission. (6) A support operator who was suspended or removed, or lost `platform.support.grant`, kept their own support grants for up to 30 days: those grants now end at once; new `supportGrantablePermissions` caps what `grantSupportAccess` can open. (7) Refused escalations and self-changes are audited as `platform.change_refused`; a no-op `setOrganizationStatus` no longer writes a platform audit entry. (8) `runPlatformCommand` and the Teams command door now reject inherited names (`__proto__`, `constructor`, `toString`) as unknown fields and copy arrays. (9) `onDecision` is no longer awaited, so a hanging hook cannot stall `can`.

## 0.5.1 - 2026-10-08

### Fixed

- **Timed suspension audit** (`suspend`, `block`, `unblock`; no migration). (1) `suspend` now refuses an `until` after the last instant of year 9999 (`membership_block_until_invalid`): SQLite compares ISO-8601 text, and a five-digit year sorted before "now", so the write was applied and then reported as `last_owner`. (2) A suspension that ends within milliseconds of being written is returned as the suspension it was (it used to fail with a false `last_owner` on PostgreSQL and SQLite). (3) `block` on a suspended member now turns the suspension into an indefinite block (new actor, reason and date, version +1) instead of silently doing nothing and letting the member come back on their own; `suspend` on a blocked member still never shortens it. **Behaviour change (0.x).** (4) `createAuditedStorage` records `membership.blocked`, `.suspended` and `.unblocked` only when something changed (a repeated call used to leave an entry claiming a decision that did not happen); `membership.blocked` carries `replacedSuspension: true` and `membership.unblocked` carries `endedSuspensionEarly: true` when they apply. (5) `leaveOrganization` refuses a blocked or suspended member (`membership_blocked`), so a sanction cannot be shed by leaving and coming back through an invitation that is still pending; an administrator removes them with `memberships.delete`. (6) `transferOwnership` refuses a recipient who is blocked or suspended (`membership_blocked`), so the organization is not left with nobody who can act. (7) **Last active Owner**: `unassignOwnerRole`, `memberships.delete` and `leaveOrganization` now refuse (`last_owner`) to remove an Owner who can still act while every other Owner is blocked or suspended; removing an Owner who is already blocked or suspended is still allowed. Memory, PostgreSQL and SQLite. **Behaviour change (0.x).**

## 0.5.0 - 2026-10-08

### Added

- **Teams** (organizational structure): `storage.teams` and `storage.teamMemberships`. A team belongs to one organization (slug and `externalId` unique inside it; every method takes the organization id and treats a team of another organization as missing; composite foreign keys enforce it in the databases), carries free-form `metadata` and `settings` (plain JSON, 16 KB) and has a lifecycle `active` → `archived` → restore, or delete when archived. A team membership links an organization membership to a team (a member can be in none, one or many) with a status `pending` / `active` / `suspended` / `removed`, a `responsibility` label (`owner`, `manager`, `member`) that grants nothing by itself, and roles of the same organization that apply inside the team only (never the Owner role). `version` / `expectedVersion` on both. Audited by `createAuditedStorage` (`team.*`, `team_member.*`). Deleting an organization membership removes its team memberships; deleting a role removes it from them, and `roles.delete(..., { members: "reject" })` counts team holders. Postgres migration `0034`, SQLite `0019`. See `guides/teams.md`. **Breaking (0.x):** `UnioraStorage` / `UnioraTransaction` gain required `teams` and `teamMemberships`, so a custom backend must implement them (the conformance suite covers them). `teamMemberships.accept` is the only way to go from `pending` to `active` and it checks that the caller is the invited person. Also: `engine.can` / `access.check` accept `teamId` (team context: active member of an active team of the organization AND the permission through organization roles or the roles held in that team; it only narrows, no Owner or manager shortcut, no support grants), and `createTeamService` is the authorized way to change teams: each operation asks the engine in the same transaction and audits the actor; nobody joins or moves between teams without `teams.members.add` (and `teams.members.remove` in the source for `moveMember`), nobody promotes themselves or gives roles they do not hold; `TEAM_PERMISSIONS` lists the keys (`teams.manage`, `teams.members.add`, `teams.members.remove`, `teams.members.manage`). New codes `team_forbidden` and `team_authorization_required`. **The storage enforces it**: every write of `teams` / `teamMemberships` takes an opaque `authorization` (a `TeamAuthorization`) that only the service and `createTrustedTeamStorage({ actor, reason })` (explicit back-office use: imports, jobs, tests) can issue; the memory, Postgres and SQLite backends verify it (`assertTeamAuthorization`) and refuse missing, forged, copied or expired tokens and tokens for another organization, operation or actor, so team changes cannot be made by accident from code that skipped the permission check.

- **Teams on invitations**: `invite({ teamIds })` offers the invitee membership of up to 10 teams of the organization. The inviter must hold `teams.members.add` (organization-wide or inside that team) when inviting (`invitation_teams_forbidden`, 403) and again when the invitation is accepted; on accept the person joins the organization and then each still-allowed team as a plain `member` (no team roles), and `accept()` returns `teams` and `teamsSkipped` (archived or deleted team, inviter lost the right, or the person already has a non-removed membership there: a suspension is never lifted this way). The preview lists `teamNames`; `Invitation.teamIds` is stored in `invitation_teams` (composite key to the team, so another organization's team is impossible and deleting the team drops the offer). Postgres migration `0035`, SQLite `0020`. **Breaking (0.x):** `Invitation` gains `teamIds` and `CreateInvitationInput` an optional `teamIds`, so a custom backend must store them (the conformance suite covers it).
- **Team hierarchy (optional)**: `Team.parentId`, set at `teams.create({ parentId })` and moved with `teams.update({ parentId })` (`null` = top level), nests a team under another active team of the same organization (8 levels at most, no loops). It is organizational only: nothing is inherited and `can({ teamId })` ignores it. New reads `teams.ancestors`, `teams.descendants` and `search({ parentId })`; new codes `team_parent_invalid`, `team_cycle`, `team_too_deep`, `team_has_children` (a team with active sub-teams cannot be archived, one with sub-teams cannot be deleted, a child cannot be restored under an archived parent). `createTeamService`: a sub-team is created by whoever has `teams.manage` in the parent team (or organization-wide); moving needs it on the team and on the destination; tree changes are serialized with an advisory lock. Audited (`team.created` carries `parentId`, `team.updated` records the move). Postgres migration `0036` (composite foreign key with the organization), SQLite `0021` (foreign key plus triggers). **Breaking (0.x):** `TeamRepository` gains required `ancestors` and `descendants`, so a custom backend must implement them (the conformance suite covers them).
- **Team routes for Express and Next**: `runTeamCommand(service, command, { actor, organizationId }, params)` (in `@uniora/core`, with `TEAM_COMMANDS`, `isTeamCommand` and `teamErrorToHttp`) runs one team service command from untrusted input: the command is fixed by the route, the actor and organization come from the session, every field is checked and an unknown one (`actor`, `authorization`, `organizationId`) is rejected; a refusal is a generic 403. `@uniora/express` adds `teamCommand(service, { command, resolve })` and `@uniora/next` `teamCommandRoute(service, { command, caller, params })`. The invitation preview now also returns `teamNames` and the accept response `teamIds` and `teamsSkipped`. No migration.
- **Teams in Studio**: a new **Teams** tab in an organization lists its teams (search, parent, member and sub-team counts) and shows one team with its path, members and their roles; an operator can create a team (optionally under a parent), archive, restore and delete it, add a member by identity, suspend, reactivate or remove a member and set its responsibility. Changes go through the trusted team storage and are audited with the usual `team.*` / `team_member.*` actions, which also appear in the activity log. English and Spanish. No migration.

## 0.4.1 - 2026-10-07

### Fixed

- **The in-memory storage returns copies**: `createMemoryStorage` used to hand out the very objects it keeps (roles from `listByOrganization` / `findByIds`, memberships, permissions, feature definitions and overrides, and what the writes return), so a record read earlier changed under the caller after `roles.update`, `assignRole`, `block` and so on, and an `expectedVersion` conflict (`role_version_conflict`, `membership_version_conflict`) could never be reproduced in tests. Every read and every write result is now a copy, as with the PostgreSQL and SQLite backends. **Behaviour change (0.x):** code that mutated a returned object and relied on the store seeing it will no longer work; use the repository methods. The conformance suite now checks it for all backends.
- **`roles.update` / `roles.rename` no longer bump `version` when nothing changes**, as `Role.version` always documented: re-saving the same name and description leaves the version alone (and a stale `expectedVersion` is still refused). The same now holds for `organizations.rename` / `update`. Applies to memory, PostgreSQL and SQLite; no migration. A real change to any field still counts. Feature overrides keep bumping on every write, as documented.

## 0.4.0 - 2026-10-07

### Added

- **Idempotent invitations**: `invitations.invite({ ..., idempotencyKey })` makes a retry safe. The first call with a key creates and sends the invitation; a later call with the same key and the same request (e-mail, roles, `ttlMs`) creates and sends nothing and returns the existing invitation with `replayed: true` and `acceptUrl: null` (the link is never stored; `resend` issues a new one); the same key with a different request fails with `invitation_idempotency_conflict` (409 `idempotency_conflict` in `invitationErrorToHttp`). Keys are scoped to the organization, 1 to 128 characters of letters, digits and `._:-`, and live as long as the invitation; a unique index backs them. Without a key nothing changes (a retry still gets `invitation_duplicate_pending`). Postgres migration `0032`, SQLite `0017`. See `guides/invitations.md`. **Breaking (0.x):** `InvitationRepository` gains a required `findByIdempotencyKey` and `CreateInvitationInput` an optional `idempotency`, so a custom backend must implement them (the conformance suite covers it).
- **Role names are unique in a normalized form**: `roles.create`, `rename`, `update` and `clone` now treat "Recepción", "recepcion" and " RECEPCIÓN " as the same name (lowercase, no diacritics, whitespace collapsed; exported as `normalizeRoleName`), so look-alikes of a role name or of "Owner" can no longer coexist in an organization. The display `name` keeps the caller's spelling and the same name can still be used in another organization. The library stores the normalized form in `roles.name_normalized` under a unique index `(organization_id, name_normalized)`, so the rule also holds when two requests race (it replaces the old exact `(organization_id, name)` index). Postgres migration `0031`, SQLite `0016`: existing roles are backfilled; if an organization already had roles that differ only in case or accents, the first (by id) keeps the plain form and the others get `#<id>` appended so the migration cannot fail, and you can rename them later. SQLite has no Unicode normalization, so its backfill covers the Latin letters with accents (U+00C0 to U+024F) and ASCII lowercase; names in other scripts keep their case in the backfill only. **Behaviour change (0.x):** a name that used to be accepted because it differed in case or accents is now refused (the same existing `RoleError`, message "A role named … already exists in this organization"). `applyRoleTemplates` uses the same rule to report a `name_taken` conflict.
- **`applyRoleTemplates` no longer stops at the first problem, and can leave existing roles alone**: `mode: "create-missing"` only creates what is missing and never rewrites an existing role, so what an Owner edited (permissions, description) survives, and `unchanged` lists the system roles left as they are. A template whose key or name is already used by a tenant's role is reported in the new `conflicts` (`key_taken`, `name_taken`) and the next templates are still applied (before, the `create` threw and the rest were never created). `continueOnError: true` records any other failure in `failed` instead of throwing (not inside a PostgreSQL transaction). The result gains `unchanged`, `conflicts` and `failed`; the default `"sync"` behaves as before and `skipped` is unchanged. No migration.
- **Optimistic concurrency for memberships and feature overrides**: `Membership.version` starts at 1 and goes up on every real change (role assigned or removed, `block`, `suspend`, `unblock`; `recordActivity`, no-ops and the automatic end of a suspension do not count). `assignRole` / `unassignRole` take `{ expectedVersion }` and `block` / `unblock` accept `expectedVersion`; a stale value fails with `membership_version_conflict` and changes nothing. A feature override carries a `version` (`EffectiveFeature.override.version`): `features.enable` / `disable(org, key, { expectedVersion })` fail with `feature_version_conflict` if the override changed since it was read, and `expectedVersion: 0` means "I saw no override yet", so two operators creating it at once cannot both win. `setMany` and `disableEverywhere` stay unconditional (they bump the version). Without `expectedVersion` everything behaves as before. Postgres migration `0033`, SQLite `0018`; existing rows start at version 1. **Breaking (0.x):** `Membership` and `Feature` gain a required `version`, and `assignRole` / `unassignRole` / `enable` / `disable` gain an optional options argument a custom backend must honour; the conformance suite covers it.
- **Optimistic concurrency for roles and organizations**: `Role.version` and `Organization.version` start at 1 and go up by one on every real change (`rename`, `update`, `setStatus` for organizations; `rename`, `update`, `setPermissions`, `grantPermission`, `revokePermission` for roles; a call that changes nothing does not count). `roles.update`, `roles.setPermissions(roleId, keys, { expectedVersion })` and `organizations.update` accept `expectedVersion`: if the record has changed since it was read, the call fails with `role_version_conflict` / `organization_version_conflict` and changes nothing, so two administrators can no longer overwrite each other. Without `expectedVersion` everything behaves as before (last write wins). Postgres migration `0030`, SQLite `0015`; existing rows start at version 1. **Breaking (0.x):** `Role` and `Organization` gain a required `version`, so a custom backend (and any code that builds these objects by hand) must provide it; the conformance suite covers it.
- **Suspended members**: `Membership.status` gains `suspended`, and `memberships.suspend(id, { actor, until, reason? })` denies the member exactly like `block` until `until` (a future date, else the new code `membership_block_until_invalid`); from that instant the membership reads `active` again by itself: `can()`, `access.check()`, snapshots, listings, filters (`status: "suspended"`), counts and the SQL functions for RLS all follow, with no job. `block` stays indefinite; `Membership.blocked` (with `until`) is present while blocked or suspended; the last active Owner can't be suspended; an already blocked or suspended member keeps their original date (`unblock` first to change it). Audit action `membership.suspended` (records `until`); the automatic reactivation writes no entry. The stored status stays `blocked` with a `blocked_until` column, so existing rows and indefinite blocks are untouched. Postgres migration `0029` (also redefines `uniora.active_membership_id`), SQLite `0014`. See `guides/core-reference.md`. **Breaking (0.x):** `MembershipRepository` gains a required `suspend` (a custom backend must implement it; the conformance suite covers it), and code that switches exhaustively on `MembershipStatus` must handle `suspended`.

## 0.3.0 - 2026-10-07

### Added

- **Commented `.sql` migrations**: every migration of `@uniora/postgres` and `@uniora/sqlite` also ships as a plain `.sql` file (`sql/` folder of each package) with a header that explains it, generated from the TypeScript migrations and checked by a test so they can't drift; `listMigrations()` returns the id and exact SQL of each. For teams that apply SQL with their own tooling. `pnpm sql:export` regenerates them. See `guides/sql-migrations.md`, and `guides/custom-backend.md` for the contract tests every storage backend must pass.
- **Support grants for platform operators**: `supportGrants.create({ id, organizationId, operator, grantedBy, reason, permissions, expiresAt })`, `revoke`, `findById`, `search`, `count` and `activePermissions`. A person who is NOT a member can act in one organization with exactly the permission keys the grant lists (and what they imply), until it expires (30 days at most) or is revoked; `can()`, `access.check()` and snapshots honour it, `onDecision` reports `via: "support_grant"`, a suspended organization or a blocked membership still denies, and the SQL functions for RLS ignore grants on purpose. Audit actions `support_grant.created` and `support_grant.revoked`. Postgres migration `0028`, SQLite `0013`. See `guides/support-grants.md`. **Breaking (0.x):** `UnioraStorage` and `UnioraTransaction` gain a required `supportGrants`, so a custom backend must implement it.
- **Entitlements (quotas per organization)**: `storage.entitlements` with `define({ key, period, defaultLimit })`, `setLimit` / `clearLimit` per organization, `get` / `list` (used, remaining, window) and `consume(org, key, amount?)` / `release`. `consume` is an atomic check-and-take, so concurrent requests never pass the limit; periods are UTC `daily`, `monthly` or `lifetime`; a limit is a whole number or `null` (unlimited). UNIORA keeps no plans or licences: the host sets the limits. Audit actions `entitlement.defined`, `entitlement.removed`, `entitlement.limit_changed`, `entitlement.limit_cleared` (consuming is not audited). Postgres migration `0027`, SQLite `0012`. See `guides/entitlements.md`. **Breaking (0.x):** `UnioraStorage` and `UnioraTransaction` gain a required `entitlements`, so a custom backend must implement it.
- **Outbox: events after commit**: `storage.outbox` (`enqueue`, `claim`, `complete`, `fail`, `requeue`, `search`, `count`, `pruneDelivered`) stores events in the same transaction as the change, and `dispatchOutbox(storage.outbox, handler, options)` delivers them from a worker: at least once, exponential backoff, parked as `dead` after `maxAttempts`, several workers at once without sharing an event (lease). `createAuditedStorage(storage, { actor, outbox: true })` also enqueues one event per audited change (type = the audit action). Error codes `outbox_event_invalid`, `outbox_payload_invalid`, `outbox_event_exists`, `outbox_claim_invalid`. Postgres migration `0026`, SQLite `0011`. See `guides/outbox.md`. **Breaking (0.x):** `UnioraStorage` and `UnioraTransaction` gain a required `outbox`, so a custom storage backend must implement it.
- **Permission groups and implied permissions**: `register({ key, group?, implies? })`: `group` is the catalog section for a role editor (`search` / `count` filter by it) and `implies` lists permissions a permission grants as well (`appointments.write` implies `appointments.read`). A role holding the bigger permission passes `can()`, `access.check()` and snapshots for everything it implies, through the whole chain; `permissions.impliedBy(key)` and `permissions.expand(keys)` expose the closure for UIs. Registration is validated: implied keys must already be registered, no self-reference or cycle, at most 20 per permission and 8 levels (`permission_implication_invalid`, `permission_group_invalid`), and `unregister` refuses a permission another one still implies (`permission_has_dependents`). The SQL function `uniora.has_permission` follows the same chain (recursive, bounded; cross-checked against the engine). Postgres migration `0025`, SQLite `0010`. **Breaking (0.x):** `register()` is a full upsert, so re-registering without `group` / `implies` clears them.
- **System roles, role templates and safer role management**: `Role.isSystem` (a role your code defines: it can't be renamed or deleted, its permissions can still change) and `Role.description`; `applyRoleTemplates(storage.roles, organizationId, templates)` gives an organization the roles your templates describe and is idempotent (creates what's missing, syncs system roles when a template changes, never touches a custom role a tenant made under the same key); `roles.setPermissions(roleId, keys)` replaces the whole list atomically and returns `{ granted, revoked }` (an unregistered key changes nothing: `role_permission_invalid`); `roles.clone(roleId, { id, name, organizationId? })` copies permissions and description into a new custom role; `roles.update(roleId, { name?, description? })`; and `roles.delete(roleId, { members: "detach" | "reject" | { reassignTo } })` (default `detach`, as before; `reject` refuses while someone holds it: `role_in_use`; `reassignTo` moves the holders to another role of the same organization first). Audit actions `role.updated`, `role.cloned`, `role.permissions_replaced`; `search` / `count` filter by `isSystem`. Postgres migration `0024`, SQLite `0009`. **Breaking (0.x):** `Role` and `RoleSummary` gain a required `isSystem`.
- **Queries across organizations**: `organizations.search({ feature: { key, enabled? } })` and `count` return the organizations where a feature is (or, with `enabled: false`, is not) effectively on (override, default and parents), combined with `status`, `query` and the keyset cursor; and `features.listEffectiveMany(organizationIds, { keys? })` resolves up to 500 organizations in ONE call (the same answers as `listEffective`, via the single effective-state rule). No migration: both use the existing tables.
- **Organization status and update**: `Organization.status` (`active` | `suspended` | `archived`, with `statusChange { at, by, reason }`) and `organizations.setStatus(id, { status, actor, reason? })`. While an organization is not `active`, `can()`, `access.check()`, snapshots and the SQL functions for RLS deny everyone in it, Owner included; the data is untouched and setting it back to `active` restores everything. `organizations.update(id, { name?, slug? })` changes both at once (validated, slug uniqueness enforced), `search` / `count` filter by `status` (one or several), and `createAuditedStorage` records `organization.updated` and `organization.status_changed` with the before and after. Postgres migration `0023`, SQLite `0008`; existing organizations are `active`. There is deliberately no hard delete: the audit trail of an organization must outlive it (archive instead; erasing personal data is a separate, later feature). **Behaviour change (0.x):** the engine now also denies when the organization itself doesn't exist, so a membership pointing at an unknown organization is denied (the SQL backends could never hold one).
- **Audit retention with a tamper-evident checkpoint**: `auditLogs.pruneBefore({ before, actor })` removes the entries older than the cut-off (never the newest one) and records a checkpoint, so the hash chain keeps verifying from there and anything edited or deleted afterwards is still detected; the removal is itself audited (`audit_log.pruned`). `applyAuditRetention(storage, { keep: { years: 5 }, actor })` is the policy as one call for a scheduled job (at least 30 days). `verifyIntegrity()` reports `pruned { through, removed }` and an anchor older than the checkpoint reads `anchor: "pruned"`. In Postgres (migration `0022`) the only way to delete is `uniora.prune_audit_logs`, `security definer`, `EXECUTE` revoked from `public`: grant it to the retention role only (see `guides/hardening.md`). SQLite: migration `0007`.
- **SQL functions for row-level security** (Postgres migration `0021`): `uniora.is_member(org)`, `uniora.has_permission(org, key)`, `uniora.is_feature_enabled(org, key)` and `uniora.has_access(org, permission, feature)` for your own policies, with the engine's exact answers (active memberships only, linked identities, Owner, feature defaults and parents). `security definer`, `stable`, pinned `search_path`, `EXECUTE` revoked from `public`, tested against an unprivileged role and cross-checked with the TypeScript engine. See `guides/rls.md`.

- **Profiles for members**: an optional `ProfileResolver` the host implements (`resolveProfiles(identities)` against its own users table or provider) and `listMembersWithProfiles(storage, resolver, options)`, which adds a `profile { displayName, email, avatarUrl }` to each listed member with ONE resolver call per page. Output is sanitised (capped strings, `http(s)` avatars only), a failing resolver never breaks the listing, and UNIORA still depends on no provider.
- **Blockable memberships**: `Membership.status` (`active` | `blocked`) with `block(id, { actor, reason })`, `unblock` and `recordActivity`. A blocked member keeps their roles but `can()`, `access.check()` and snapshots deny everything; the last active Owner can't be blocked; listings and counts filter by status. Memberships also carry `createdAt`, `updatedAt`, `invitedBy` (filled when they come from an invitation) and `lastActiveAt`. Postgres migration `0019`, SQLite `0005`; memberships that predate it get the migration time as `createdAt`.
