    How it works

    Authentication and authorization, separately.

    UNIORA lets you use the identity provider you prefer (Google, GitHub, Clerk, Auth0…) and manage authorization on its own, with fully customizable rules, roles and permissions.

    Your app
    Secure, controlled access

    Not an auth provider

    It never sees passwords or sessions. Your provider identifies the user; UNIORA decides what that user can do in an organization.

    Not a SaaS

    No central service holds your data. Everything lives in a dedicated uniora.* schema in your PostgreSQL, or in SQLite.

    Provider-agnostic

    Switch from Supabase to Clerk, or run Auth0 alongside it, without rewriting authorization. Identity links keep a user's organizations and roles when they change provider.

    Mission

    Give every product a secure, provider-independent way to answer: who can do what, in which organization?

    UNIORA replaces hand-written multi-tenancy, roles, invitations, feature flags and audit trails with one tested core.

    • Secure by default: unknown, missing or inconsistent means DENY
    • Your data stays in your database
    • Membership is always verified, never assumed
    Vision

    Change auth provider without rewriting who can do what.

    Authentication is replaceable. Authorization models your business: organizations, responsibilities, capabilities and quotas. It should outlast any vendor.

    • One model across Supabase, Clerk, Auth0, Better Auth and future providers
    • Every decision explainable, every change audited
    • On the roadmap: resource-level permissions, role inheritance, per-organization policies

    One system. Endless possibilities.

        Security
        
      The security your business needs.
      
        
      Each guarantee is enforced in code and covered by tests. Several are enforced by database constraints, not only by application logic.
      
        
        
          
      • Strict logical isolation between organizations
        • 
          
      • Granular access policies
        • 
          
      • Full audit and traceability
        • 
          
      • Ready to scale
        • 
        
      
      
      
      
      
        
      
        
      
      
    
      

    
      
      
      01
      Deny by default
      The engine grants access only when it can justify it. Unknown permission, missing membership, wrong organization or suspended tenant: DENY.
      can() → false
      
      
      02
      Every organization has an owner
      Each organization is created with a protected Owner. The last Owner cannot be removed, blocked or demoted. A database constraint enforces this under concurrent requests.
      last_owner ✕
      
      
      03
      Tamper-evident audit log
      Append-only and hash-chained. Editing or deleting an entry is detected by verifyIntegrity(). Changes made through Studio, invitations and identity links are recorded in the same transaction.
      sha256 ⛓ sha256
      
      
      04
      Permissions, features and quotas
      Permissions define what a user can do. Features define what an organization has unlocked. Quotas count seats and reports atomically. Each is modeled separately.
      permission + feature + quota
      
      
      05
      Framework-independent core
      @uniora/core has no dependency on Next.js, Express or any database driver. Storage adapters pass one shared conformance suite.
      core ← adapters
      
      
      06
      The server decides
      React helpers such as <Can> only shape the UI. The browser never reaches your database; the server computes the decision and authorizes every real operation.
      UI hides · server decides

      Pricing
      
      Keep the free tier. Skip the B2B add-on.
      
      
      Auth providers charge extra for organizations, custom roles and permissions. UNIORA provides them in your own database at no license cost. Keep your provider for login and drop the B2B tier.
